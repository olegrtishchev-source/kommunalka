Часть 1. На телефоне

Шаг 1. Включить режим разработчика.



Открой Настройки → О телефоне (у разных производителей: «О устройстве», «Об устройстве»).



Найди строку «Номер сборки» (Build number) — на MIUI (Xiaomi/Redmi/POCO) вместо неё нажимай «Версия MIUI».



Нажми на неё 7 раз подряд. Появится сообщение «Вы стали разработчиком» / «Режим разработчика включён».



Шаг 2. Включить отладку по USB.



Вернись в Настройки → Система → Для разработчиков.

Варианты пути в зависимости от производителя:



Samsung: Настройки → Параметры разработчика.



Xiaomi / Redmi / POCO: Настройки → Расширенные настройки → Для разработчиков.



Huawei / Honor: Настройки → Система и обновления → Для разработчиков.



Pixel / «чистый» Android: Настройки → Система → Для разработчиков.



Найди пункт «Отладка по USB» (USB debugging) и включи его.



Подтверди предупреждение «Разрешить отладку по USB?» — OK.



Шаг 3. Дополнительно (зависит от производителя).



Xiaomi: включи также «Установка через USB» (Install via USB) — на некоторых Redmi переключатель неактивен, пока не привязан Mi-аккаунт и/или не вставлена SIM-карта с номером; может появиться с задержкой после первого включения режима разработчика.



Huawei: может потребоваться «Разрешить отладку по USB» + «Проверять приложения через USB».



Samsung: кроме отладки может понадобиться установить драйверы Samsung USB Driver с официального сайта.



Шаг 4. Подключить телефон к компьютеру.



Подключи телефон кабелем USB к ПК. Кабель должен быть не «только для зарядки» — иначе данные не пойдут.



На телефоне появится системное окно «Разрешить отладку по USB?». Поставь галочку «Всегда разрешать с этого компьютера» и нажми «Разрешить».



Опусти шторку уведомлений на телефоне → выбери режим USB «Передача файлов» (File Transfer / MTP), не «Только зарядка».

Шаг 7. Если adb devices пуст — разбор причин.



Причина	Что делать

На телефоне не включена отладка по USB	Вернуться к шагу 2

Режим USB стоит «Только зарядка»	Переключить в «Передача файлов» (MTP)

Windows не видит устройство вообще	Проверить в Диспетчере устройств: должно появиться «Android Device» или «ADB Interface»; если там «Неизвестное устройство» — нужен драйвер

Supabase: полная схема записана в supabase/schema.sql (5 таблиц, индексы под нужные выборки, unique(channel_id, reading_date) и unique(supplier_id, period) как защита от дублей, триггер автообновления updated_at). RLS сознательно не включён этим скриптом — политики добавляются отдельно на Этапе 2.3, тогда же скрипт накатывается в Supabase SQL Editor (нужен доступ к аккаунту Олега, у Claude его нет). Решение: user_id хранится на каждой таблице (кроме receipts, где владелец выводится через payment_id → supplier), а не только на suppliers — денормализация ради простых и быстрых RLS-политик без JOIN.

Зеркальная схема drift (Этап 3.4, для справки уже сейчас):

| Supabase | drift | Примечание |
|---|---|---|
| uuid | TextColumn | в SQLite нет типа uuid, id хранится как текст |
| text | TextColumn | |
| numeric(x,y) | RealColumn | double; для сумм личного бюджета точности достаточно, отдельный тип "деньги в копейках" — избыточная сложность для этого проекта |
| boolean | BoolColumn | |
| date / timestamptz | DateTimeColumn | |
| jsonb (reading_snapshot, bank_details) | TextColumn | сериализуется/десериализуется вручную через jsonEncode/jsonDecode при чтении и записи |
| enum (type, status) | TextColumn | значения те же английские литералы; в Dart-коде — свой enum + маппинг туда-обратно |
| внешние ключи | TextColumn (без .references()) | *решение изменено на 3.4, см. ниже — drift.references() в использованной версии drift_dev не генерирует реальный REFERENCES в SQLite, а локальный FK и не нужен: см. журнал 3.4 |

Функция guardRepositoryCall(action) — обёртка вызова; добавлена во все сетевые вызовы во всех пяти репозиториях (Supplier/Reading/Channel/Payment/Receipt — refresh/create/update/archive/delete/attach/getUrl), но не в StorageService.compress() (чистая локальная операция) и не в AuthService (там разбор ошибок сознательно оставлен экранам ещё с 3.2 — другая, ранее принятая граница, не переигрываем).

Базовый уровень намеренно, как и назван пункт плана: распознаются самые частые случаи (нет сети; PostgrestException/StorageException/AuthException как есть), а не исчерпывающий список типов исключений — то, чего нет ни в одном catch, проходит насквозь необёрнутым. Дополнительно распознаются две конкретные ошибки Postgres по коду: 23505 (unique_violation — «такая запись уже существует», для readings(channel_id, reading_date) и payments(supplier_id, period), см. schema.sql) и 23503 (foreign_key_violation — «нельзя удалить, есть ссылки», подстраховка на случай гонки при ChannelRepository.delete).

Доменные исключения репозиториев (MeterValueDecreasedException, ChannelHasReadingsException) guardRepositoryCall не трогает — они бросаются до сетевого вызова, как и были задуманы на 3.6/3.6b.
