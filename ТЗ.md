# Техническое задание

## Приложение для учёта показаний счётчиков и оплаты ЖКУ

Версия 2.1 · черновик для личного использования · только Android

\---

## 1\. Назначение и цели

Приложение предназначено для личного использования (один пользователь, одно устройство — смартфон на Android). Заменяет ручной учёт показаний счётчиков в Excel и разрозненные квитанции единым инструментом, который:

* хранит карточки поставщиков коммунальных услуг с их банковскими реквизитами и тарифом;
* принимает текущие показания счётчика и автоматически считает сумму к оплате (для поставщиков без счётчика — принимает сумму к оплате напрямую);
* формирует платёжный QR-код (реквизиты, сумма) для загрузки в банковское приложение и показывает реквизиты для оплаты; сам платёж пользователь выполняет в своём банковском приложении — прямой интеграции с банком нет;
* позволяет заполнить карточку поставщика сканированием QR-кода с квитанции, чтобы не вводить реквизиты вручную;
* помогает передать показания поставщику тем способом, который он принимает (платёжная форма банка, личный кабинет, e-mail);
* сохраняет чек об оплате и ведёт историю платежей;
* синхронизирует данные с облаком (Supabase), чтобы они не терялись при переустановке приложения или смене телефона;
* формирует Excel-отчёт по итогам месяца и выгружает его на Яндекс.Диск.

## 2\. Целевая аудитория и режим использования

Один пользователь, личное некоммерческое использование. Многопользовательский режим, роли, публичный доступ — не предусмотрены.

## 3\. Платформы и технологический стек

|Компонент|Решение|
|-|-|
|Клиент|Flutter, целевая платформа — Android|
|Хранение и синхронизация данных|Supabase (решение зафиксировано, см. обоснование ниже)|
|Локальный офлайн-кеш|`drift` (SQLite) — полноценная локальная БД. У Supabase, в отличие от Firebase Firestore, нет встроенного офлайн-кеша (работает через HTTP) — без `drift` не будет офлайн-просмотра уже загруженных данных|
|Хранение чеков (фото/скан)|Supabase Storage|
|Хранение Excel-отчётов|Яндекс.Диск (REST API, OAuth-авторизация) — отдельно от Supabase Storage, см. §4.10|
|Формирование Excel|Пакет `excel` (чистый Dart, свободная лицензия) — без регистрации и лицензионных ключей; формулы Excel не нужны, суммы считает само приложение, из форматирования нужна только заливка ячеек цветом|
|Аутентификация|Вход и регистрация в личном аккаунте (email+пароль) — оба экрана реализуются в приложении, доступ только для одного пользователя|
|Управление состоянием|Riverpod — асинхронная работа с Supabase и локальным стримом drift удобнее вести через Riverpod (меньше boilerplate, проще тестировать)|

### Обоснование выбора Supabase

Firebase не подходит по нескольким причинам: вендор-лок (данные в формате Google, миграция на другой сервис сложна и болезненна); бесплатный тариф Spark (1 ГБ хранилища, 50 000 чтений/день) может упереться в лимит на чеках; региональные риски — как сервис Google, Firebase/Google Cloud Console может быть недоступен или ограничен с российского IP; и главное — единственное практическое преимущество Firebase (полноценная нативная поддержка FlutterFire на Android) не даёт выигрыша именно потому, что у Supabase на Android всё работает точно так же надёжно.

Supabase: работает через обычные HTTP-запросы (REST/Realtime API), а не через нативные SDK — доступен без VPN; бесплатный тариф щедрее (500 МБ базы + 1 ГБ Storage); Postgres, а не NoSQL — привычная табличная модель и SQL; не привязан к экосистеме Google.

Решение подтверждено практически (см. Этап 1 плана выполнения — минимальный спайк с записью/чтением через Supabase).

## 4\. Функциональные требования

### 4.1 Управление поставщиками услуг

* Добавление, редактирование и удаление (мягкое — архивирование) карточки поставщика. Удалённый (архивный) поставщик пропадает из активного списка, но связанные показания и платежи (включая `reading\\\\\\\_snapshot`) остаются в истории без изменений.
* Поля карточки: название («ТНС Энерго Кубань», «Газпром межрегионгаз» и т.п.), категория/иконка, банковские реквизиты для оплаты (получатель, ИНН, КПП — необязательно, БИК, номер счёта, название банка и корр. счёт — необязательно, назначение платежа — шаблон с подстановкой периода), лицевой счёт (необязательно), способы передачи показаний (см. §4.12), тариф (руб. за единицу измерения), единица измерения (кВт·ч, м³ и т.п.).
* **Тип поставщика** — «с показаниями» (СВЕТ, ГАЗ, ВОДА — расчёт по формуле показания × тариф, см. §4.2–4.3) или «без показаний» (МУСОР, Интернет и подобные — фиксированной суммы нет, сумма к оплате вводится вручную каждый период, см. §4.3). Для типа «без показаний» поля каналов (единица измерения, тариф, показания) не запрашиваются — это допустимо для поставщиков с фиксированной суммой (вывоз мусора) и с суммой, которую пользователь смотрит каждый раз сам (например, интернет/ТВ — сумма берётся из личного кабинета поставщика).
* У поставщика есть **адрес (объект)** — см. §4.13 (например, одно из двух жилых помещений пользователя).
* Для поставщика «с показаниями» может быть больше одного «канала» показаний и тарифа (например, свет: день/ночь; вода: горячая/холодная) — гибкая, а не жёстко фиксированная схема полей. По умолчанию у нового поставщика один канал; кнопка «Добавить канал» явно доступна в форме, чтобы не терялась возможность завести второй тариф. Канал можно удалить только если по нему ещё нет ни одного сохранённого показания (например, если канал добавили по ошибке); канал хотя бы с одним показанием удалить нельзя, доступны только переименование/редактирование.
* Канал может быть **производным** — не иметь собственных показаний, а брать расход из канала другого поставщика за тот же период (пример из практики: «Канализация» — отдельный поставщик со своими реквизитами и оплатой, но расход для неё считается по показаниям «Воды», отдельного счётчика на канализацию не существует). У производного канала есть свой тариф, но нет собственных записей показаний — пользователь их не вводит.
* Карточку можно заполнить сканированием QR-кода с квитанции (см. §4.11) или вручную.
* Список поставщиков — главный экран приложения (карточки).

### 4.2 Показания счётчиков

Относится только к поставщикам типа «с показаниями». Для производного канала (см. §4.1) ввод показаний недоступен — расход подтягивается автоматически из канала-источника за тот же период. Если по каналу-источнику ещё нет показания за нужный период, ввод по производному каналу временно недоступен (нужно сначала внести показание источника).

* Ввод текущего показания по каждому «каналу» поставщика.
* Приложение подтягивает предыдущее сохранённое показание автоматически. Ввод показаний предполагается строго последовательным по времени — «предыдущее» всегда является последним по дате сохранённым показанием; ввод пропущенных показаний задним числом в MVP не поддерживается (возможное расширение после MVP).
* Валидация: текущее показание не должно быть меньше предыдущего. Понижение блокируется, если только показание явно не помечено флагом `meter\\\\\\\_replaced` («счётчик заменён») — тогда ограничение снимается осознанно, а не через общее предупреждение.
* Дата снятия показания сохраняется вместе со значением.

### 4.3 Расчёт суммы к оплате

* Для поставщика «с показаниями»: `расход = текущее\\\\\\\_показание − предыдущее\\\\\\\_показание`; `сумма = расход × тариф`. Если у поставщика несколько каналов — сумма считается по каждому каналу и суммируется в итоговую сумму к оплате. Результат (предпросмотр) показывается пользователю сразу на экране ввода показаний, ещё до создания записи о платеже. Для производного канала расход и предыдущее/текущее значения в `reading\\\\\\\_snapshot` копируются из последнего снимка канала-источника за тот же период, а тариф и итоговая сумма — свои.
* Для поставщика «без показаний»: сумма к оплате вводится вручную при создании платежа за период (не фиксированная величина — может отличаться от месяца к месяцу).
* Сущность `Payment` создаётся в момент перехода с экрана ввода показаний (или, для поставщика без показаний, с экрана ввода суммы) на экран оплаты (одним действием «Далее»). Для поставщика «с показаниями» в этот момент фиксируется `reading\\\\\\\_snapshot` — неизменяемый снимок использованных показаний; для поставщика «без показаний» `reading\\\\\\\_snapshot` не заполняется (сумма и так самодостаточна).
* Период платежа (`Payment.период`) определяется автоматически по текущей дате (или дате снятия показания, если применимо); на экране оплаты его можно скорректировать вручную (актуально, если показания/сумма вносятся в начале следующего месяца за предыдущий период).

### 4.4 Шаг «оплата»

* Экран с расчётной суммой, реквизитами поставщика (с возможностью скопировать), платёжным QR-кодом (см. ниже) и коротким напоминанием, что оплата выполняется через банковское приложение пользователя.
* Реальный перевод денег приложение не выполняет — интеграции с банковским API нет и не предусмотрена.
* **Платёжный QR-код.** Кнопка «QR для оплаты» формирует QR по стандарту ГОСТ Р 56042-2014: строка `ST00012|Ключ=Значение|…`, кодировка UTF-8. Всегда: `Name` (получатель), `PersonalAcc` (счёт), `BIC`, `PayeeINN`. Если заполнены в карточке: `BankName`, `CorrespAcc`, `KPP`, `persAcc` (лицевой счёт). `Sum` — расчётная сумма в копейках (целое число). `Purpose` — назначение платежа по шаблону с подставленным периодом.
* QR можно сохранить в галерею телефона и загрузить как изображение в банковском приложении (подтверждено на практике: приложение банка принимает QR-код из галереи), а также отправить через системное меню «Поделиться».
* Показание счётчика (для «с показаниями» — по каждому каналу) показывается крупно рядом с QR: в банковской форме строка «Показания счётчика» вводится вручную — в QR квитанций реальных поставщиков полей `CounterId`/`CounterVal` нет. Возможность передать показание внутри самого QR проверяется экспериментом (п. 5.14 плана); если банк подхватит поле, оно добавится в QR как необязательное.
* Запасной вариант, если QR по какой-то причине не подошёл, — кнопки копирования отдельных реквизитов.
* Пользователь вводит **фактически оплаченную сумму** (по умолчанию предзаполнена расчётной суммой, можно исправить — оплата бывает не равна расчёту: с запасом, округлением, частями). Банк, через который прошла оплата, отдельным полем не фиксируется — эта информация видна на самом чеке (см. 4.5).
* Статус платежа выставляется автоматически по соотношению факта и расчёта: **ожидает** (факт не введён), **частично оплачено** (0 < факт < расчёт), **оплачено** (факт ≥ расчёт). Факт-сумму и статус можно откорректировать позже (например, если ошиблись при вводе).
* Прикрепление чека — отдельное, необязательное сразу же действие: можно прикрепить сразу после ввода оплаты, а можно вернуться к этому платежу позже (в истории) и прикрепить чек тогда.

### 4.5 Чек об оплате

* Прикрепление фото (камера) или файла (выбор из галереи/файлов) в качестве подтверждения оплаты — в любой момент после создания платежа, не обязательно сразу.
* Перед загрузкой изображение сжимается (уменьшение разрешения и качества), целевой размер — не более \~500 КБ на файл. Это нужно, чтобы бесплатный лимит облачного хранилища (1 ГБ Storage у Supabase) не закончился через пару лет накопления чеков.
* Чек привязывается к конкретному платежу и поставщику, хранится в облаке вместе с остальными данными. Ссылка на чек — кликабельная, открывает файл чека (в интерфейсе приложения и в Excel-отчёте).

### 4.6 История платежей

* Список платежей по каждому поставщику: дата, показания (текущее/предыдущее, если применимо), расход, расчётная сумма, факт-сумма, статус, чек.
* Статус «оплачено» — не только текстовая пометка, но и визуальный маркер (соответствующий цвет/иконка в списке), чтобы быстро видеть картину без чтения каждой строки.
* Общий список платежей по всем поставщикам с фильтрацией по поставщику/периоду, а также поиском по сумме и по дате.

### 4.7 Синхронизация

* Данные (поставщики, показания, платежи, чеки), созданные или изменённые в приложении, сохраняются в Supabase и доступны оттуда же — в том числе после переустановки приложения или при входе с другого Android-устройства под тем же аккаунтом.
* Механизм синхронизации — pull: обновление данных при запуске приложения, открытии экрана и свайпом вниз (pull-to-refresh), без постоянного соединения/realtime-подписок. Supabase Realtime-подписки — возможное расширение после MVP, если pull на практике окажется недостаточно отзывчивым.
* В версии MVP офлайн поддерживает только просмотр уже загруженных данных; создание новых записей требует подключения к интернету. Создание записей офлайн с последующей синхронизацией (очередь отложенных изменений) — расширение после того, как MVP подтверждён рабочим (см. план).

### 4.8 Настройки приложения

* Валюта (по умолчанию — рубли).
* Формат даты (по умолчанию — дд.мм.гггг).
* Включение/выключение локальных напоминаний о внесении показаний (если реализованы, см. §6 плана).
* Выход из аккаунта.
* Очистка локального кеша (`drift`) с последующей повторной загрузкой данных из облака.

### 4.9 Резервное копирование

* Экспорт всех данных пользователя (поставщики, показания, платежи — без файлов чеков) в один JSON-файл.
* Импорт из такого файла — на случай потери доступа к аккаунту Supabase или необходимости восстановить данные вручную.

### 4.10 Отчётность

* Приложение формирует Excel-отчёт по заданному периоду (обычно — месяц) на основе данных о платежах. Колонки (по образцу личной таблицы учёта, которую заменяет приложение): Поставщик, Текущие (показания), Предыдущие (показания), Расход, Тариф, Сумма (расчётная), Оплачено по факту, Дата оплаты, Чек (кликабельная ссылка), Статус (с зелёной заливкой для «оплачено»). Строка «ИТОГО» — сумма факт-оплат за период. Для поставщиков без показаний колонки Текущие/Предыдущие/Расход/Тариф остаются пустыми.
* Отчёт создаётся заново при каждом формировании, а не дописывается в существующий файл — пакет `excel` не поддерживает чтение уже существующих xlsx-файлов, только создание новых.
* Имя файла — с номером периода: `Отчёт\\\\\\\_<Месяц>\\\\\\\_<Год>.xlsx` (например, `Отчёт\\\\\\\_Январь\\\\\\\_2026.xlsx`), чтобы файлы разных месяцев не терялись и не путались.
* Готовый файл выгружается на Яндекс.Диск через REST API с OAuth-авторизацией — не в Supabase Storage (тот уже занят чеками), а туда, где к отчёту есть прямой доступ с любого устройства через обычный веб-интерфейс, без привязки к самому приложению. Google Drive не рассматривается — известные проблемы доступа и оплаты для российских пользователей; Яндекс.Диск даёт 10 ГБ бесплатно, доступен без VPN, работает с российскими картами.
* Формирование и выгрузка отчёта — по кнопке пользователя, и/или автоматически в рамках сценария «Закрытие месяца» (см. §8).

### 4.11 Заполнение карточки поставщика по QR с квитанции

* В форме добавления/редактирования поставщика — кнопка «Заполнить по QR с квитанции». Источник: камера или изображение из галереи (в том числе скриншот квитанции из личного кабинета).
* Приложение разбирает строку формата ГОСТ Р 56042 и подставляет значения в поля формы. Сохранение — только после подтверждения пользователем, все поля остаются редактируемыми.
* Правила разбора (составлены по образцам квитанций трёх реальных поставщиков: «ТНС энерго Кубань» — заголовок `ST00011`, ЕИРЦ и «Водопровод» — `ST00012`):

  * ключи регистронезависимы (`persAcc` и `PersAcc`, `payerAddress` и `PayerAddress` — один и тот же ключ);
  * значение отделяется по **первому** знаку `=` (в ссылках он встречается многократно);
  * неизвестные ключи игнорируются, разбор из-за них не падает;
  * строка, не начинающаяся с `ST0001`, → сообщение «QR не распознан», ручной ввод остаётся доступным;
  * последний знак заголовка — код кодировки (1 — Windows-1251, 2 — UTF-8, 3 — KOI8-R); корректность кириллицы проверяется на реальных квитанциях на устройстве (п. 5.10 плана).
* Соответствие ключей QR полям карточки:

|Ключ QR|Поле карточки|
|-|-|
|`Name`|получатель|
|`PersonalAcc`|номер счёта (расчётный счёт получателя)|
|`BankName`|название банка|
|`BIC`|БИК|
|`CorrespAcc`|корр. счёт|
|`PayeeINN`|ИНН|
|`KPP`|КПП (если ключа нет — поле пустое; у части поставщиков его нет)|
|`persAcc` / `PersAcc`|лицевой счёт (это счёт плательщика, не путать с `PersonalAcc`)|
|`A3Pay`|ссылка на страницу поставщика (`cabinet\\\\\\\_url`), к способам передачи показаний добавляется `cabinet`|

* Не переносятся: `Sum` и `PaymPeriod` (сумму считает приложение по показаниям, период задаётся отдельно), `Message`, `payerAddress`/`PayerAddress`, `TechCode` и прочие неизвестные ключи.
* Ссылка `A3Pay` содержит персональный код доступа и хранится только в записи пользователя в Supabase (защищена RLS).

### 4.12 Передача показаний поставщику

Приложение не отправляет показания самостоятельно (у поставщиков нет открытого API для физлиц, §6) — оно подготавливает данные и открывает нужный канал. В карточке поставщика задаются один или несколько способов (`reading\\\\\\\_methods`):

* **`bank\\\\\\\_form` — в платёжной форме банка.** Показание вводится в банковском приложении при оплате; приложение показывает его крупно рядом с платёжным QR (§4.4).
* **`cabinet` — личный кабинет или страница поставщика.** Кнопка копирует показание в буфер обмена и открывает ссылку `cabinet\\\\\\\_url`.
* **`email` — письмо.** Кнопка открывает почтовое приложение с готовым письмом: адрес `reading\\\\\\\_email`, тема, текст (лицевой счёт, период, показание). Пользователь отправляет письмо сам.
* Если способ не задан — действие не показывается («не передаю»).
* Для производного канала (например, канализация, §4.1) в письме и на экране используется показание канала-источника (воды).
* Действия доступны на экране оплаты (§4.4) после сохранения показания.

### 4.13 Адреса (объекты)

Пользователь оплачивает ЖКУ по двум адресам (две квартиры — например, «Черноморская» и «Советская»). Чтобы платежи и поставщики разных адресов не смешивались, у поставщика есть **адрес**.

* Адрес — **свободный текст** у карточки поставщика (например, «Черноморская», «Советская»); отдельного справочника адресов нет — адресов мало (личное использование), проще текстовое поле, как категория.
* На главном экране (список поставщиков) — **переключатель адреса**: чипы по адресам, которые реально встречаются у поставщиков, плюс «Все». Список поставщиков фильтруется по выбранному адресу.
* Список адресов для чипов **собирается из данных** (какие адреса заполнены у поставщиков), а не задаётся жёстко — если появится третий адрес, он появляется в переключателе сам.
* Выбранный адрес **запоминается** между запусками приложения (чтобы при следующем открытии не выбирать заново).
* Поставщики **без адреса** показываются только при выборе «Все».
* Адрес — часть карточки поставщика; на фильтры истории и отчётов в MVP не влияет (при необходимости добавим отдельно).

## 5\. Нефункциональные требования

* Данные — банковские реквизиты поставщиков и история платежей пользователя — не должны быть общедоступны; доступ только из личного аккаунта пользователя (авторизация обязательна, публичного/анонимного общего доступа нет). Лицевые счета и персональные ссылки личных кабинетов хранятся только в записях пользователя (RLS) и не выводятся в Excel-отчёт.
* Приложение не должно требовать постоянного подключения к интернету для просмотра уже загруженных данных.
* Минималистичный, понятный интерфейс — без лишней визуальной сложности, разрабатывается один человек для себя.
* Должна быть предусмотрена возможность резервного копирования данных (экспорт/импорт JSON) — на случай сбоя облачного сервиса или ошибки пользователя.

## 6\. Что явно вне рамок проекта

* Windows desktop-версия и любая другая платформа, кроме Android (iOS/macOS/Linux/Web-версии тоже не предусмотрены).
* Автоматическое списание/перевод денег через банковские API (оплата через API банка рассмотрена 29.09.2026 и отклонена как невыгодная).
* Многопользовательский режим, роли, публикация в сторах (Google Play) — приложение для личного использования, установка вручную. Обновление — через новый `flutter build apk --release` и переустановку файла; номер версии ведётся в `pubspec.yaml`.
* Интеграция с официальными API поставщиков услуг (у большинства нет открытого API для физлиц).

## 8\. Пользовательские сценарии

1. **Добавление нового поставщика** — пользователь создаёт карточку — вручную или отсканировав QR с квитанции (реквизиты подставляются сами) — указывает тип (с показаниями/без), реквизиты, тариф, каналы показаний (если применимо) и способы передачи показаний.
2. **Ежемесячный ввод показаний или суммы** — открывает карточку поставщика → для «с показаниями» видит предыдущее показание и вводит текущее (видит расход и сумму); для «без показаний» вводит сумму к оплате за период. Показание передаётся поставщику способом, заданным в карточке (§4.12).
3. **Оплата** — переходит на экран оплаты → видит реквизиты, расчётную сумму и платёжный QR → сохраняет QR в галерею и загружает его в банковское приложение (показание, если поставщик принимает его в форме оплаты, вводит там же) → оплачивает через банк → вводит факт-сумму → статус выставляется автоматически → прикрепляет чек.
4. **Просмотр истории** — открывает историю по поставщику или общую, видит все платежи со статусами и чеками.
5. **Закрытие месяца** — после того как все поставщики за период оплачены, приложение формирует Excel-отчёт по месяцу и выгружает его на Яндекс.Диск.

## 9\. Критерии готовности (Definition of Done)

* Приложение собирается и запускается на Android.
* Можно создать карточку поставщика (с показаниями или без) с реквизитами и тарифом (один или несколько каналов).
* Можно ввести показание (или сумму для поставщика без счётчика), получить корректный расчёт.
* Есть экран оплаты с реквизитами, вводом факт-суммы, автоматическим статусом.
* На экране оплаты формируется платёжный QR, который принимает банковское приложение (загрузка из галереи).
* Карточку поставщика можно заполнить сканированием QR с квитанции.
* Для каждого способа передачи показаний (платёжная форма банка, личный кабинет, e-mail) есть рабочее действие.
* Можно прикрепить и сохранить чек, ссылка на него кликабельна.
* Можно сформировать Excel-отчёт по месяцу (с заливкой оплаченных строк и строкой «ИТОГО») и выгрузить его на Яндекс.Диск.
* История платежей корректно синхронизируется с Supabase — данные сохраняются в облаке и доступны после переустановки приложения.
* Приложение переживает потерю интернет-соединения без потери данных.

## 10\. MVP — минимальная версия для первой сквозной проверки

Прежде чем наращивать полный функционал (несколько каналов, чеки, история, фильтры, настройки, отчётность, офлайн-создание), собирается и проверяется тончайшая рабочая связка:

* один поставщик, один тариф, без каналов;
* одно показание, расчёт суммы;
* связь приложения с Supabase подтверждена практически: запись, созданная приложением, сохраняется в Supabase и корректно читается обратно.

Только после того, как это работает, добавляется остальной функционал из разделов 4.1–4.10 — по одному пункту за раз, как и предусмотрено планом выполнения.
