# Техническое задание

## Приложение для учёта показаний счётчиков и оплаты ЖКУ

Версия 2.0 · черновик для личного использования · только Android

---

## 1. Назначение и цели

Приложение предназначено для личного использования (один пользователь, одно устройство — смартфон на Android). Заменяет ручной учёт показаний счётчиков в Excel и разрозненные квитанции единым инструментом, который:

- хранит карточки поставщиков коммунальных услуг с их банковскими реквизитами и тарифом;
- принимает текущие показания счётчика и автоматически считает сумму к оплате (для поставщиков без счётчика — принимает сумму к оплате напрямую);
- показывает реквизиты для оплаты и служит напоминанием (сам платёж пользователь выполняет через своё банковское приложение — прямой интеграции с банком нет);
- сохраняет чек об оплате и ведёт историю платежей;
- синхронизирует данные с облаком (Supabase), чтобы они не терялись при переустановке приложения или смене телефона;
- формирует Excel-отчёт по итогам месяца и выгружает его на Яндекс.Диск.

## 2. Целевая аудитория и режим использования

Один пользователь, личное некоммерческое использование. Многопользовательский режим, роли, публичный доступ — не предусмотрены.

## 3. Платформы и технологический стек

| Компонент | Решение |
|---|---|
| Клиент | Flutter, целевая платформа — Android |
| Хранение и синхронизация данных | Supabase (решение зафиксировано, см. обоснование ниже) |
| Локальный офлайн-кеш | `drift` (SQLite) — полноценная локальная БД. У Supabase, в отличие от Firebase Firestore, нет встроенного офлайн-кеша (работает через HTTP) — без `drift` не будет офлайн-просмотра уже загруженных данных |
| Хранение чеков (фото/скан) | Supabase Storage |
| Хранение Excel-отчётов | Яндекс.Диск (REST API, OAuth-авторизация) — отдельно от Supabase Storage, см. §4.10 |
| Формирование Excel | Пакет `excel` (чистый Dart, свободная лицензия) — без регистрации и лицензионных ключей; формулы Excel не нужны, суммы считает само приложение, из форматирования нужна только заливка ячеек цветом |
| Аутентификация | Вход и регистрация в личном аккаунте (email+пароль) — оба экрана реализуются в приложении, доступ только для одного пользователя |
| Управление состоянием | Riverpod — асинхронная работа с Supabase и локальным стримом drift удобнее вести через Riverpod (меньше boilerplate, проще тестировать) |

### Обоснование выбора Supabase

Firebase не подходит по нескольким причинам: вендор-лок (данные в формате Google, миграция на другой сервис сложна и болезненна); бесплатный тариф Spark (1 ГБ хранилища, 50 000 чтений/день) может упереться в лимит на чеках; региональные риски — как сервис Google, Firebase/Google Cloud Console может быть недоступен или ограничен с российского IP; и главное — единственное практическое преимущество Firebase (полноценная нативная поддержка FlutterFire на Android) не даёт выигрыша именно потому, что у Supabase на Android всё работает точно так же надёжно.

Supabase: работает через обычные HTTP-запросы (REST/Realtime API), а не через нативные SDK — доступен без VPN; бесплатный тариф щедрее (500 МБ базы + 1 ГБ Storage); Postgres, а не NoSQL — привычная табличная модель и SQL; не привязан к экосистеме Google.

Решение подтверждено практически (см. Этап 1 плана выполнения — минимальный спайк с записью/чтением через Supabase).

## 4. Функциональные требования

### 4.1 Управление поставщиками услуг

- Добавление, редактирование и удаление (мягкое — архивирование) карточки поставщика. Удалённый (архивный) поставщик пропадает из активного списка, но связанные показания и платежи (включая `reading_snapshot`) остаются в истории без изменений.
- Поля карточки: название («ТНС Энерго Кубань», «Газпром межрегионгаз» и т.п.), категория/иконка, банковские реквизиты для оплаты (получатель, ИНН, КПП, БИК, номер счёта, назначение платежа — шаблон с подстановкой периода), тариф (руб. за единицу измерения), единица измерения (кВт·ч, м³ и т.п.).
- **Тип поставщика** — «с показаниями» (СВЕТ, ГАЗ, ВОДА — расчёт по формуле показания × тариф, см. §4.2–4.3) или «без показаний» (МУСОР, Интернет и подобные — фиксированной суммы нет, сумма к оплате вводится вручную каждый период, см. §4.3).
- Для поставщика «с показаниями» может быть больше одного «канала» показаний и тарифа (например, свет: день/ночь; вода: горячая/холодная) — гибкая, а не жёстко фиксированная схема полей. По умолчанию у нового поставщика один канал; кнопка «Добавить канал» явно доступна в форме, чтобы не терялась возможность завести второй тариф. Канал можно удалить только если по нему ещё нет ни одного сохранённого показания (например, если канал добавили по ошибке); канал хотя бы с одним показанием удалить нельзя, доступны только переименование/редактирование.
- Список поставщиков — главный экран приложения (карточки).

### 4.2 Показания счётчиков

Относится только к поставщикам типа «с показаниями».

- Ввод текущего показания по каждому «каналу» поставщика.
- Приложение подтягивает предыдущее сохранённое показание автоматически. Ввод показаний предполагается строго последовательным по времени — «предыдущее» всегда является последним по дате сохранённым показанием; ввод пропущенных показаний задним числом в MVP не поддерживается (возможное расширение после MVP).
- Валидация: текущее показание не должно быть меньше предыдущего. Понижение блокируется, если только показание явно не помечено флагом `meter_replaced` («счётчик заменён») — тогда ограничение снимается осознанно, а не через общее предупреждение.
- Дата снятия показания сохраняется вместе со значением.

### 4.3 Расчёт суммы к оплате

- Для поставщика «с показаниями»: `расход = текущее_показание − предыдущее_показание`; `сумма = расход × тариф`. Если у поставщика несколько каналов — сумма считается по каждому каналу и суммируется в итоговую сумму к оплате. Результат (предпросмотр) показывается пользователю сразу на экране ввода показаний, ещё до создания записи о платеже.
- Для поставщика «без показаний»: сумма к оплате вводится вручную при создании платежа за период (не фиксированная величина — может отличаться от месяца к месяцу).
- Сущность `Payment` создаётся в момент перехода с экрана ввода показаний (или, для поставщика без показаний, с экрана ввода суммы) на экран оплаты (одним действием «Далее»). Для поставщика «с показаниями» в этот момент фиксируется `reading_snapshot` — неизменяемый снимок использованных показаний; для поставщика «без показаний» `reading_snapshot` не заполняется (сумма и так самодостаточна).
- Период платежа (`Payment.период`) определяется автоматически по текущей дате (или дате снятия показания, если применимо); на экране оплаты его можно скорректировать вручную (актуально, если показания/сумма вносятся в начале следующего месяца за предыдущий период).

### 4.4 Шаг «оплата»

- Экран с расчётной суммой, реквизитами поставщика (с возможностью скопировать) и коротким напоминанием, что оплата выполняется через банковское приложение пользователя.
- Реальный перевод денег приложение не выполняет — интеграции с банковским API нет и не предусмотрена.
- Пользователь вводит **фактически оплаченную сумму** (по умолчанию предзаполнена расчётной суммой, можно исправить — оплата бывает не равна расчёту: с запасом, округлением, частями) и **банк**, через который прошла оплата (свободный текст).
- Статус платежа выставляется автоматически по соотношению факта и расчёта: **ожидает** (факт не введён), **частично оплачено** (0 < факт < расчёт), **оплачено** (факт ≥ расчёт). Факт-сумму и статус можно откорректировать позже (например, если ошиблись при вводе).
- Прикрепление чека — отдельное, необязательное сразу же действие: можно прикрепить сразу после ввода оплаты, а можно вернуться к этому платежу позже (в истории) и прикрепить чек тогда.

### 4.5 Чек об оплате

- Прикрепление фото (камера) или файла (выбор из галереи/файлов) в качестве подтверждения оплаты — в любой момент после создания платежа, не обязательно сразу.
- Перед загрузкой изображение сжимается (уменьшение разрешения и качества), целевой размер — не более ~500 КБ на файл. Это нужно, чтобы бесплатный лимит облачного хранилища (1 ГБ Storage у Supabase) не закончился через пару лет накопления чеков.
- Чек привязывается к конкретному платежу и поставщику, хранится в облаке вместе с остальными данными. Ссылка на чек — кликабельная, открывает файл чека (в интерфейсе приложения и в Excel-отчёте).

### 4.6 История платежей

- Список платежей по каждому поставщику: дата, показания (текущее/предыдущее, если применимо), расход, расчётная сумма, факт-сумма, банк оплаты, статус, чек.
- Статус «оплачено» — не только текстовая пометка, но и визуальный маркер (соответствующий цвет/иконка в списке), чтобы быстро видеть картину без чтения каждой строки.
- Общий список платежей по всем поставщикам с фильтрацией по поставщику/периоду, а также поиском по сумме и по дате.

### 4.7 Синхронизация

- Данные (поставщики, показания, платежи, чеки), созданные или изменённые в приложении, сохраняются в Supabase и доступны оттуда же — в том числе после переустановки приложения или при входе с другого Android-устройства под тем же аккаунтом.
- Механизм синхронизации — pull: обновление данных при запуске приложения, открытии экрана и свайпом вниз (pull-to-refresh), без постоянного соединения/realtime-подписок. Supabase Realtime-подписки — возможное расширение после MVP, если pull на практике окажется недостаточно отзывчивым.
- В версии MVP офлайн поддерживает только просмотр уже загруженных данных; создание новых записей требует подключения к интернету. Создание записей офлайн с последующей синхронизацией (очередь отложенных изменений) — расширение после того, как MVP подтверждён рабочим (см. план).

### 4.8 Настройки приложения

- Валюта (по умолчанию — рубли).
- Формат даты (по умолчанию — дд.мм.гггг).
- Включение/выключение локальных напоминаний о внесении показаний (если реализованы, см. §6 плана).
- Выход из аккаунта.
- Очистка локального кеша (`drift`) с последующей повторной загрузкой данных из облака.

### 4.9 Резервное копирование

- Экспорт всех данных пользователя (поставщики, показания, платежи — без файлов чеков) в один JSON-файл.
- Импорт из такого файла — на случай потери доступа к аккаунту Supabase или необходимости восстановить данные вручную.

### 4.10 Отчётность

- Приложение формирует Excel-отчёт по заданному периоду (обычно — месяц) на основе данных о платежах: поставщик, показания (если применимо), расход, расчётная сумма, факт-сумма, банк оплаты, статус (с зелёной заливкой для «оплачено»), кликабельная ссылка на чек, строка «ИТОГО» — сумма факт-оплат за период.
- Отчёт создаётся заново при каждом формировании, а не дописывается в существующий файл — пакет `excel` не поддерживает чтение уже существующих xlsx-файлов, только создание новых.
- Имя файла — с номером периода: `Отчёт_<Месяц>_<Год>.xlsx` (например, `Отчёт_Январь_2026.xlsx`), чтобы файлы разных месяцев не терялись и не путались.
- Готовый файл выгружается на Яндекс.Диск через REST API с OAuth-авторизацией — не в Supabase Storage (тот уже занят чеками), а туда, где к отчёту есть прямой доступ с любого устройства через обычный веб-интерфейс, без привязки к самому приложению. Google Drive не рассматривается — известные проблемы доступа и оплаты для российских пользователей; Яндекс.Диск даёт 10 ГБ бесплатно, доступен без VPN, работает с российскими картами.
- Формирование и выгрузка отчёта — по кнопке пользователя, и/или автоматически в рамках сценария «Закрытие месяца» (см. §8).

## 5. Нефункциональные требования

- Данные — банковские реквизиты поставщиков и история платежей пользователя — не должны быть общедоступны; доступ только из личного аккаунта пользователя (авторизация обязательна, публичного/анонимного общего доступа нет).
- Приложение не должно требовать постоянного подключения к интернету для просмотра уже загруженных данных.
- Минималистичный, понятный интерфейс — без лишней визуальной сложности, разрабатывается один человек для себя.
- Должна быть предусмотрена возможность резервного копирования данных (экспорт/импорт JSON) — на случай сбоя облачного сервиса или ошибки пользователя.

## 6. Что явно вне рамок проекта

- Windows desktop-версия и любая другая платформа, кроме Android (iOS/macOS/Linux/Web-версии тоже не предусмотрены).
- Автоматическое списание/перевод денег через банковские API.
- Многопользовательский режим, роли, публикация в сторах (Google Play) — приложение для личного использования, установка вручную. Обновление — через новый `flutter build apk --release` и переустановку файла; номер версии ведётся в `pubspec.yaml`.
- Интеграция с официальными API поставщиков услуг (у большинства нет открытого API для физлиц).

## 7. Модель данных (сущности)

- **Supplier** (поставщик): id, название, категория, тип (`с_показаниями` / `без_показаний`), банковские реквизиты (объект), шаблон назначения платежа `period_template` (например, «оплата за {месяц} {год}»), список каналов (`channels`: название канала, единица измерения, текущий тариф) — только для типа `с_показаниями`.
- **Reading** (показание): id, supplier_id, channel_id, значение, дата, `meter_replaced` (bool — показание после замены счётчика, ограничение «не меньше предыдущего» для него не применяется). Существует только для поставщиков типа `с_показаниями`.
- **Payment** (платёж): id, supplier_id, период, `reading_snapshot` (для поставщика `с_показаниями` — неизменяемый самодостаточный снимок всех данных расчёта на момент создания платежа: по каждому каналу `channel_id`, название канала, единица измерения, предыдущее значение, текущее значение, **тариф на момент расчёта**, дата снятия показания; для поставщика `без_показаний` — пусто), расход, расчётная сумма, **факт-сумма** (фактически оплаченная, может быть меньше расчётной — частичная оплата), **банк оплаты**, статус (`ожидает` / `частично_оплачено` / `оплачено` — вычисляется автоматически по соотношению факт-суммы и расчётной), дата оплаты, ссылка на чек (необязательна, кликабельная).
- **Receipt** (чек): id, payment_id, файл (фото/скан), дата загрузки.

## 8. Пользовательские сценарии

1. **Добавление нового поставщика** — пользователь создаёт карточку, указывает тип (с показаниями/без), реквизиты, тариф, каналы показаний (если применимо).
2. **Ежемесячный ввод показаний или суммы** — открывает карточку поставщика → для «с показаниями» видит предыдущее показание и вводит текущее (видит расход и сумму); для «без показаний» вводит сумму к оплате за период.
3. **Оплата** — переходит на экран оплаты → видит реквизиты и расчётную сумму → оплачивает через банк → вводит факт-сумму и банк → статус выставляется автоматически → прикрепляет чек.
4. **Просмотр истории** — открывает историю по поставщику или общую, видит все платежи со статусами и чеками.
5. **Закрытие месяца** — после того как все поставщики за период оплачены, приложение формирует Excel-отчёт по месяцу и выгружает его на Яндекс.Диск.

## 9. Критерии готовности (Definition of Done)

- Приложение собирается и запускается на Android.
- Можно создать карточку поставщика (с показаниями или без) с реквизитами и тарифом (один или несколько каналов).
- Можно ввести показание (или сумму для поставщика без счётчика), получить корректный расчёт.
- Есть экран оплаты с реквизитами, вводом факт-суммы и банка, автоматическим статусом.
- Можно прикрепить и сохранить чек, ссылка на него кликабельна.
- Можно сформировать Excel-отчёт по месяцу (с заливкой оплаченных строк и строкой «ИТОГО») и выгрузить его на Яндекс.Диск.
- История платежей корректно синхронизируется с Supabase — данные сохраняются в облаке и доступны после переустановки приложения.
- Приложение переживает потерю интернет-соединения без потери данных.

## 10. MVP — минимальная версия для первой сквозной проверки

Прежде чем наращивать полный функционал (несколько каналов, чеки, история, фильтры, настройки, отчётность, офлайн-создание), собирается и проверяется тончайшая рабочая связка:

- один поставщик, один тариф, без каналов;
- одно показание, расчёт суммы;
