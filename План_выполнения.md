Изменения 29.09.2026 — оплата и передача показаний (ТЗ v2.1)

Контекст: идея оплаты через API банковского счёта не подтвердилась (невыгодно), выпущена версия ТЗ 2.1 без банковского API. Решения по итогам обсуждения и проверки на практике:

1. Оплата: приложение формирует платёжный QR по ГОСТ Р 56042 (ST00012, UTF-8) из реквизитов поставщика и расчётной суммы, сохраняет его в галерею; пользователь загружает QR как изображение в банковском приложении. Проверено на практике: приложение банка принимает QR из галереи.
2. Заполнение карточки: сканирование QR с квитанции (камера или галерея). Проверены QR трёх реальных поставщиков — ТНС энерго Кубань (ST00011, есть ссылка A3Pay, нет КПП), ЕИРЦ (ST00012, есть PaymPeriod), Водопровод (ST00012, есть КПП, TechCode). Выводы для парсера: ключи регистронезависимы (persAcc/PersAcc), значение — по первому «=», неизвестные ключи игнорируются, PersonalAcc (счёт получателя) ≠ persAcc (лицевой счёт плательщика).
3. Передача показаний: полей CounterId/CounterVal в QR квитанций нет — показание вводится в банковской форме вручную, приложение показывает его крупно рядом с QR. Дополнительно: личный кабинет (ссылка + копирование значения; для ТНС энерго ссылка приходит из QR — A3Pay) и письмо на e-mail (вода и канализация принимают показания при оплате или письмом).
4. Изменения модели (ТЗ §7): Supplier — personal\_account, reading\_methods (text\[]), cabinet\_url, reading\_email; bank\_details — bank\_name, corr\_account. Нужны: ALTER TABLE в Supabase (выполняет Олег в SQL Editor), поднятие schemaVersion drift 4 → 5, правка модели/репозитория/формы поставщика (пункт 5.8).

✅ 2.2. Спроектировать структуру таблиц в Supabase и зеркальную схему drift — выполнено (23.09.2026).

Supabase: полная схема записана в supabase/schema.sql (5 таблиц, индексы под нужные выборки, unique(channel\_id, reading\_date) и unique(supplier\_id, period) как защита от дублей, триггер автообновления updated\_at). RLS сознательно не включён этим скриптом — политики добавляются отдельно на Этапе 2.3, тогда же скрипт накатывается в Supabase SQL Editor (нужен доступ к аккаунту Олега, у Claude его нет). Решение: user\_id хранится на каждой таблице (кроме receipts, где владелец выводится через payment\_id → supplier), а не только на suppliers — денормализация ради простых и быстрых RLS-политик без JOIN.

|uuid|TextColumn|в SQLite нет типа uuid, id хранится как текст|
|text|TextColumn||
|numeric(x,y)|RealColumn|double; для сумм личного бюджета точности достаточно, отдельный тип "деньги в копейках" — избыточная сложность для этого проекта|

✅ 3.9. Базовая обработка ошибок сети/сервера на уровне репозиториев — выполнено (24.09.2026).

lib/repositories/repository\_exceptions.dart — общая для всех репозиториев точка перевода низкоуровневых исключений в два понятных типа: NetworkException (SocketException/TimeoutException — запрос не дошёл, нет интернета/таймаут) и ServerException (PostgrestException/StorageException/AuthException — запрос дошёл, сервер ответил ошибкой). Функция guardRepositoryCall(action) — обёртка вызова; добавлена во все сетевые вызовы во всех пяти репозиториях (Supplier/Reading/Channel/Payment/Receipt — refresh/create/update/archive/delete/attach/getUrl), но не в StorageService.compress() (чистая локальная операция) и не в AuthService (там разбор ошибок сознательно оставлен экранам ещё с 3.2 — другая, ранее принятая граница, не переигрываем).

Базовый уровень намеренно, как и назван пункт плана: распознаются самые частые случаи (нет сети; PostgrestException/StorageException/AuthException как есть), а не исчерпывающий список типов исключений — то, чего нет ни в одном catch, проходит насквозь необёрнутым. Дополнительно распознаются две конкретные ошибки Postgres по коду: 23505 (unique\_violation — «такая запись уже существует», для readings(channel\_id, reading\_date) и payments(supplier\_id, period), см. schema.sql) и 23503 (foreign\_key\_violation — «нельзя удалить, есть ссылки», подстраховка на случай гонки при ChannelRepository.delete).

Доменные исключения репозиториев (MeterValueDecreasedException, ChannelHasReadingsException) guardRepositoryCall не трогает — они бросаются до сетевого вызова, как и были задуманы на 3.6/3.6b.

Показ этих ошибок пользователю (перевод в текст на экране, retry-кнопки и т.п.) — уже дело экранов Этапа 4, не репозиториев.
